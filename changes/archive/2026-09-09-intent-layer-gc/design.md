## Context

`scripts/spec.mjs` (366 lines) is the whole intent layer: `new`, `status`, `validate`, `archive`,
`stage`. It reads and writes only files that are already on disk, has no dependencies, and is
exercised end to end as a child process by `test/spec.test.mjs` (16 tests today, each with its
own temp root via `test/helpers.mjs:runSpec`). `npm test` runs that file together with
`test/completion-guard.test.mjs` (15 tests), for the 31 that pass today.

Today `changes/` has exactly one exit. `archive` (`scripts/spec.mjs:318`) refuses unless every
box is ticked and a PASS report exists under `.my-flow/verify/`, then merges delta specs and
moves the directory. A change that is dropped after `interview` or superseded during `mf-plan`
has nowhere to go, so it stays in the active area, appears in every `spec status`, and keeps a
delta that can silently overwrite a later change's delta when archived out of order
(`mergeDelta`, `scripts/spec.mjs:289`). `specs/` has the mirror problem: `validateSpecFile`
(`scripts/spec.mjs:135`) checks structure only, so a capability can accumulate requirements
that contradict each other or describe behavior the code no longer has, and every one of them
passes.

Two facts were established by running the current script rather than reading it:

- `node scripts/spec.mjs status --stale-days 30 --root <tmp>` prints `30: (missing)`. The flag
  loop at `scripts/spec.mjs:30-33` consumes a value only for `--root`; every other `--flag`
  is skipped but its value falls through into `positional`, where it is read as a change name.
  Any new value-taking flag must be added to that branch or it silently breaks `status`.
- A `<!-- via: 2026-09-09-demo -->` line placed directly under `### Requirement: Foo` in a main
  spec produces no validation error, while removing the scenario from the same file still
  produces `requirement "Foo" has no "#### Scenario:"`. So `validateSpecFile` already tolerates
  the provenance marker: the marker work is a test to lock that in, not a parser change.

Everything under `skills/`, `codex/`, `agents/` and `.claude-plugin/plugin.json` is generated by
`scripts/build.mjs` from `src/` plus `manifest.json`; `npm run check` fails when they drift.

## Goals / Non-Goals

**Goals:**

- Give `changes/` a third exit (`abandon`) that leaves a record and never touches `specs/`.
- Make `spec status` surface the three kinds of rot the layer accumulates: changes nobody is
  working on, deltas that collide, and capabilities nobody has re-checked against the code.
- Give every merged requirement a one-line pointer back to the change that produced it, so an
  audit can be cheap.
- Add a read-only `mf-audit` skill that judges a capability against the code and hands its
  findings back into the normal change flow.
- Keep the whole thing inside one script, one new skill source file, and their tests.

**Non-Goals:**

Inherited verbatim from `proposal.md` Non-Goals, and not restated here: no deletion or
compaction of `changes/archive/`, no script-authored requirement text beyond the single
provenance comment, no script-side spec-vs-code checking, no change to the completion-guard
hook, no simple-mode (`docs/changes/<name>.md`) support for the new subcommands, no new
`STAGES` entry, no automatic `RENAMED` merge, no new dependencies.

Additionally out of scope for this change:

- No change to `archive`'s PASS gate or to `--force` semantics anywhere.
- No new subagent role, and no edit to `src/agents/*.md`. `mf-audit` carries its own report
  template in the delegation prompt, the way `src/skills/mf-verify.md:44` already does.
- No `session-context.mjs` change, even though it also lists active changes.

## Assumptions

These were the four "Needs the user" boundaries in `proposal.md`; they were settled before
planning and are recorded here so `execute` does not re-open them.

1. Item 6 (the audit nudge) stays in scope.
2. All eight README files are updated, in one task group at the end, kept to one row or one
   sentence per new behavior so the group can be split off if it grows.
3. No change to `archive`'s PASS gate, to `hooks/`, or to `STAGES`.
4. The provenance marker is exactly `<!-- via: <YYYY-MM-DD>-<name> -->` on its own line,
   immediately after the `### Requirement:` heading.

## Decisions

### Principles

- **P1 - Detect, never mutate.** Every signal this change adds is a printed warning. The only
  bytes a script writes into `specs/` remain the single provenance comment.
- **P2 - Derive state, never store it.** Staleness comes from file mtimes, overlap from the
  delta files themselves, the audit nudge from directory names under `changes/archive/`. No
  new state file, no counter, no cache.
- **P3 - One script, no new abstractions.** `spec.mjs` grows functions, not modules. No option
  parser, no shared library, no dependency.
- **P4 - Additive output.** Existing `status` rows and existing JSON fields keep their exact
  shape and meaning. New signals are new lines and new keys, so the 31 current tests keep
  passing unchanged.
- **P5 - Behavior and test in the same task.** No task adds a script behavior without the test
  that observes it from a child-process run.

### Decision drivers

- **D1 - Reversibility.** Nothing added here may destroy intent. `abandon` moves a directory
  and never merges; the marker is a comment; audits are reports.
- **D2 - Zero new user surface.** No new stage, no config file, no environment variable that
  must be set for the defaults to work.
- **D3 - Observability from a temp root.** Every behavior must be assertable by
  `runSpec(root, [...])` plus `utimesSync`, with no git repository and no network.

### D-1: How staleness is measured

- **(a) Newest recursive mtime under `changes/<name>/`.** Zero dependencies, works in a temp
  root, matches the `utimesSync` test approach the proposal already names.
- **(b) `git log -1 --format=%ct -- changes/<name>`.** True authorship time, immune to
  checkout, but requires a git repository, spawns a process per change, and fails in exactly
  the temp-root fixtures the suite is built on.
- **(c) An `updated` timestamp written into the state file per change.** Violates P2 and only
  ever tracks the current change.

**Chosen: (a).** D3 decides it. The cost is stated in Risks: a fresh clone resets mtimes and
clears every stale mark.

Implementation: a six-line recursive walk using `readdirSync(dir, { withFileTypes: true })` and
`statSync`, returning the maximum `mtimeMs`. The `recursive` option of `readdirSync` is
deliberately not used; it landed in Node 20.1 while `package.json` engines say `>=20`.

### D-2: How `--stale-days` and `--reason` are parsed

- **(a) Add both to the value-consuming branch at `scripts/spec.mjs:31`,** next to `--root`.
  Two lines. Keeps the loop the only argument code in the file.
- **(b) A small generic option parser** that consumes a value for any flag in a known set.
  More correct in the abstract, but it is a new abstraction for two flags (P3), and it changes
  how `--json` and `--force` are read, which risks the existing tests.

**Chosen: (a).** The evidence in Context shows this is a correctness fix, not a nicety: without
it `status --stale-days 30` reads `30` as a change name.

Resolution order for both new numeric settings, highest first: the CLI flag, then the
environment variable, then the default. `--stale-days` and `MY_FLOW_STALE_DAYS`, default 14
(the range the proposal permits is 7 to 30). `MY_FLOW_AUDIT_EVERY`, default 5 (range 3 to 10).
A non-numeric or non-positive value falls back to the default rather than failing, because
`status` must never exit non-zero over a formatting problem.

### D-3: Where delta-overlap detection lives

- **(a) `status` only.** Cheapest, but the warning arrives when nobody is about to act on it.
- **(b) `validate` only.** Right before the gate, but invisible in the daily command.
- **(c) Both, from one memoized helper.** `overlapIndex()` builds a map from capability plus
  requirement name to the list of claims, each claim being a change name and the delta section
  that claims it, once per process. `status` prints every entry with two or more changes;
  `validate` attaches the entries that involve the change being validated as warnings.

**Chosen: (c).** The helper is the whole cost; wiring it into the second command is three
lines. Overlaps stay warnings in `validate`, never errors, because the proposal says detection
only and because two changes may legitimately land in sequence.

Each claim carries its section kind, and the warning prints it:
`overlap: <cap> "<Req>" in changes <a> (MODIFIED) and <b> (REMOVED)`. Without the kind, an
ADDED-versus-REMOVED collision, which is a genuine contradiction, is indistinguishable from two
changes both modifying the same requirement, which is often a legitimate sequence.

RENAMED sections are included, but they cannot be read the same way. `splitRequirements`
(`scripts/spec.mjs:267`) matches only `### Requirement:` headings, while a RENAMED entry is a
`- FROM: ### Requirement: <name>` line parsed by the regex at `scripts/spec.mjs:242`. The helper
therefore collects ADDED, MODIFIED and REMOVED names through `splitRequirements` and RENAMED
names by reusing that FROM regex. A rename claiming the same requirement another change is
modifying is exactly the collision worth reporting, so dropping RENAMED would leave the sharpest
case invisible.

### D-4: How `abandon` shares code with `archive`

- **(a) Extract `moveToArchive(name, suffix)`** from the tail of the `archive` block: create
  `changes/archive/<date>-<name><suffix>`, `renameSync`, and set the state to `archived` when
  the moved change was current. `archive` passes an empty suffix, `abandon` passes
  `-abandoned`.
- **(b) Duplicate the six lines in the `abandon` block.** Avoids touching working code, but the
  state-file rule then exists twice and will drift.

**Chosen: (a).** The refactor is behavior-preserving and is guarded by the two existing archive
tests, which must keep passing before `abandon` is written. That ordering is task 4.1.

`abandon` gates, in order: the change must exist; `proposal.md` must contain an `## Abandoned`
section carrying a `**Reason**:` line, where `--reason "..."` appends that section and line
before the check; and the change must not be fully ticked unless `--force`, because a fully
ticked change is an `archive`, not an abandonment. Delta specs are never read.

### D-5: Provenance marker format and replacement

- **(a) An HTML comment as the first line after the heading** (fixed by assumption 4). Invisible
  in rendered markdown, already tolerated by `validateSpecFile` per the Context evidence, and
  carried along by `splitRequirements` (`scripts/spec.mjs:267`) because the block is sliced
  from the heading to the next heading.
- **(b) A bold `Via` line.** Renders as content, so it reads as part of the requirement and
  invites hand-editing.
- **(c) A trailer at the end of the block.** Lost the moment a MODIFIED delta replaces the
  block, which is exactly when the marker matters.

**Chosen: (a).**

Replacement: `mergeDelta` gains a fourth parameter `via`, the string `<date>-<name>`, and stamps
each ADDED and MODIFIED block before `blocks.set`. The stamp is strip-then-insert: first delete
every line in the block that matches a via-marker, anywhere in the block and not only on the
line after the heading, then insert one marker directly after the `### Requirement:` heading.
Stripping globally matters because a MODIFIED delta is usually produced by copying the current
block out of `specs/`, and a hand-edited copy can leave the old marker in the middle of the
text. Exactly one marker per merged block is the invariant the test asserts. REMOVED blocks are
deleted, so they are never stamped, and `abandon` never merges, so it never stamps.

### D-6: Which role `mf-audit` delegates to

- **(a) `architect`.** Its contract is already "read-only design reviewer and diagnosis
  advisor" that must cite `path:line` for every structural claim and must separate root cause
  from symptoms (`src/agents/architect.md:12-22`). Deciding whether a written requirement still
  matches the built system is that judgment. It runs on opus in `manifest.json`.
- **(b) `verifier`.** Its contract is bound to completion claims and to criteria derived from
  `tasks.md` (`src/agents/verifier.md:16-18`), and its PASS / FAIL / INCOMPLETE vocabulary
  implies a gate on a change. An audit has no change and no completion claim, so the role would
  have to be argued out of its own instructions. It also runs on sonnet.
- **(c) A new `auditor` role.** Rejected under P3: a fifth role means two more generated files,
  a manifest entry, and a contract to maintain, for a job an existing role already describes.

**Chosen: (a) architect.** Both roles deny `Write`, so in either case the skill's own context
writes the report file, exactly as `src/skills/mf-verify.md:40` does with the verifier. The
delegation prompt states that the report template replaces the role's default output block.

### D-7: Keeping audit reports out of the archive PASS gate

`archive` accepts any file under `.my-flow/verify/` whose name starts with the change name plus
a hyphen and whose text matches `/Verdict:\s*PASS/` (`scripts/spec.mjs:329`). The proposal fixes
audit reports at `.my-flow/verify/audit-<cap>-<timestamp>.md`, which prefix-matches a change
literally named `audit`.

- **(a) The audit report heading is `### Status: CLEAN | DRIFT | BROKEN`, never `Verdict`.**
  Zero code, and it removes the only way an audit could satisfy the gate.
- **(b) Move audit reports to `.my-flow/audit/`.** Cleaner separation, but the report location
  is fixed by the proposal, so changing it needs the user.

**Chosen: (a).** This is a hard rule in the skill body, not a suggestion.

### D-8: How the audit nudge counts merges

Derived entirely from `changes/archive/` (P2). Directory names are `<YYYY-MM-DD>-<name>`, so a
lexicographic sort is chronological across days.

`changes/archive/` must be guarded with `existsSync` before it is read. It does not exist in
this repository, and `spec new` never creates it; only `scripts/init.mjs:53` does. Since the
nudge runs whenever `specs/` exists, an unguarded `readdirSync` would throw ENOENT on exactly
the projects that have specs but have never archived anything.

For each capability directory under `specs/`: find the last archived directory that is an audit
marker for that capability, then count the directories after it that contain `specs/<cap>/spec.md`
and whose name does not end in `-abandoned`. Abandoned changes are excluded from the count
because their deltas were never merged. When the count reaches `MY_FLOW_AUDIT_EVERY` (default 5),
`status` prints `audit suggested: <cap> (<count> merges since last audit)`.

The audit marker match is anchored, not a substring test:

```
^\d{4}-\d{2}-\d{2}-(?:.*-)?audit-<cap>(?:-abandoned)?$
```

A substring test for `-audit-<cap>` is wrong: for the capability `spec`, the directory
`2026-01-01-audit-spec-helper` contains `-audit-spec` and would silently clear the wrong
capability's counter. The anchor requires the capability name to run to the end of the directory
name, optionally followed by `-abandoned`. Only capability names matching `[a-z0-9][a-z0-9-]*`
take part in the nudge, which is what makes it safe to interpolate the name into the pattern
without escaping.

Note the asymmetry between the two uses of `-abandoned`: an abandoned audit directory still
counts as an audit marker (it is the record that an audit happened), while an abandoned change
never counts as a merge.

**The clean-audit escape hatch.** A CLEAN audit produces no findings, so it produces no change,
so nothing is ever archived and the nudge never clears. It would fire on every `status` forever.
The recorded way to close a clean audit is therefore:

```
node scripts/spec.mjs new audit-<cap>
node scripts/spec.mjs abandon audit-<cap> --reason "audit clean, no findings"
```

That leaves `changes/archive/<date>-audit-<cap>-abandoned/` holding the proposal and the reason,
merges nothing, touches no spec, and resets the counter through the `(?:-abandoned)?` branch of
the anchor. `mf-audit` recommends exactly this in its output when the status is CLEAN.

Capabilities are enumerated from `specs/`, not from archived deltas, because the nudge is about
re-checking truth that exists. A project without `specs/` gets no nudges and no directory scan.

### D-9: Output shape

`status` text keeps its existing one-row-per-change block, then appends warning lines. A stale
row gains the suffix ` [stale 23d]`. JSON gains `stale` (boolean) and `lastModified` (ISO
string) per row, and a top-level `warnings` array of strings holding the state warning, the
overlap warnings, and the audit nudges in that order. Existing keys are untouched (P4). A row
that is fully ticked is never marked stale: a finished change waiting to be archived is not rot.

The state warning fires when `.my-flow/state/current-change.json` names a change that is stale
or no longer exists, and is suppressed when its stage is `archived`. Without that suppression it
would fire after every successful `archive`, since `archive` leaves the state pointing at a
directory it just moved.

### D-10: The `mf-audit` skill body

`src/skills/mf-audit.md`, registered in `manifest.json` with the Claude override
`allowed-tools: Read Grep Glob Bash Agent Write`. Frontmatter carries `name`, `description`, and
`argument-hint: "<capability | all>"`; the tool-specific fields live in the manifest, as they do
for every other skill. House style follows `src/skills/mf-verify.md`: an `Input: {{ARGS}}` line,
numbered steps, and a `<!-- MY-FLOW:CLAUDE -->` / `<!-- MY-FLOW:CODEX -->` pair around the
delegation mechanics only.

Steps:

1. Resolve the argument: one capability directory under `specs/`, or `all` for every one of
   them. Stop with a message if `specs/` is missing or the capability is unknown.
2. Build the inventory from `specs/<cap>/spec.md`: each `### Requirement:` name, its
   `<!-- via: ... -->` marker if present, and its scenario names. The marker is the starting
   point for tracing a requirement back to its proposal in `changes/archive/`.
3. Delegate one capability per agent run to the read-only `architect` role, passing the spec
   path, the inventory, and the source and test roots. Claude uses the Agent tool with
   `subagent_type: my-flow:architect`; Codex spawns the native `architect` subagent.

   The delegation prompt must override the role's loop, not merely its output format. The
   architect's loop begins by reading `proposal.md` and `design.md` and listing the files they
   name (`src/agents/architect.md:25-26`), which an audit does not have: there is no change and
   no proposal, only a capability spec and the code. Its output block also hard-codes
   `## Verdict: CLEAR | WATCH | BLOCK` (`src/agents/architect.md:33`). The prompt therefore
   states explicitly that, for this run, steps 1 and 2 of the loop are replaced by "read
   `specs/<cap>/spec.md` and, for each requirement in the inventory, open the source and test
   files that would implement it", and that the report template below replaces the output block
   in full, including the `Verdict` line. What carries over unchanged is the rest of the role's
   contract: never judge code it has not opened, cite `path:line` for every claim, separate root
   cause from symptom, and never edit a file.
4. Write the returned report to `.my-flow/verify/audit-<cap>-<timestamp>.md` from this context.
   The role denies `Write`, so the skill saves the file. Before writing, scan the returned text
   for any line matching `Verdict:`. If one is present, the role fell back to its default output
   block; rewrite that line to the `### Status:` form, or send the report back for one correction
   round. Never write a report containing the word `Verdict` (D-7).
5. Relay the status line, the counts per section, and the suggested change name. When the status
   is CLEAN, recommend the two-command clean-audit record from D-8 so the nudge clears.

Report template:

```
## Spec Audit: <capability>
### Status: CLEAN | DRIFT | BROKEN
### Inventory (requirement | via | evidence path:line)
### Unimplemented requirements
### Undocumented behavior (code or tests with no requirement)
### Contradictions
### Misplaced requirements (belongs in <capability>)
### Suggested change: <kebab-case-name>
```

Hard rules stated in the body: the skill never edits `specs/` and never edits
`changes/archive/`; its only output is the report. Fixes go through `spec new <name>`, then
`mf-plan` with REMOVED / MODIFIED / RENAMED deltas, then `execute`, `mf-verify`, and
`spec archive`. The report never uses the word `Verdict`, enforced by the step 4 scan, so it can
never satisfy the archive PASS gate (D-7). The suggested change name must end in `audit-<cap>`
so that archiving or abandoning it clears the audit nudge under the anchored pattern in D-8.

## Risks / Trade-offs

- **mtime is not authorship time.** A fresh clone, a checkout, or a worktree switch rewrites
  every mtime and clears every stale mark. Accepted: stale is a nudge printed by `status`, never
  a gate, and D-1 records the alternative if this becomes a real complaint.
- **`status` now scans `changes/archive/`.** Cost is one `readdirSync` plus one `existsSync` per
  archived directory per capability, on a command that used to touch only active changes. Fine
  at tens of archived changes; revisit past a few hundred.
- **The nudge under-counts.** A change that modified a capability without shipping a delta spec
  is invisible to the count. Under-counting suggests audits too rarely rather than too often,
  which is the safe direction.
- **`changes/archive/` stops meaning "all merged".** Abandoned changes land there with unmerged
  deltas. The `-abandoned` suffix is the only marker, and both the nudge count and any future
  archive reader must respect it.
- **`status` output grows.** Anything parsing the text form will see new trailing lines. JSON
  consumers are safe by P4, and that is the interface the tests use.
- **Audit reports sit next to verification reports, and the filename genuinely collides.**
  `archive` scans `.my-flow/verify/` for files whose name starts with the change name plus a
  hyphen (`scripts/spec.mjs:329`). A report named `audit-spec-helper-<ts>.md` satisfies that
  prefix test for a change literally named `audit-spec-helper`, which is precisely the name
  `mf-audit` suggests and the name the clean-audit record uses. The prefix collision is real and
  is not fixed here; what prevents harm is the second half of the gate, the `/Verdict:\s*PASS/`
  match, which an audit report can never satisfy because step 4 of the skill rejects any line
  containing `Verdict` before writing. Two consequences: the `Verdict` scan is load-bearing, not
  cosmetic, and if a later change loosens that gate to match on filename alone, an audit report
  would let an audit change be archived without verification.
- **Archive sorting is chronological only across days.** Directory names begin with `YYYY-MM-DD`,
  so a lexicographic sort orders days correctly but orders same-day archives by change name. The
  audit nudge can therefore miscount by one when an audit change and a merge are archived on the
  same day and the merge sorts before the audit. The count is a nudge, not a gate, so a one-off
  off-by-one is tolerable; a stricter ordering would need a timestamp the directory name does
  not carry.
- **`moveToArchive` refactors working code.** Mitigated by running the existing archive tests
  before `abandon` is written (task 4.1).

## Rebuild / Re-run After Change

- `npm run build` after any edit to `src/skills/*.md`, `src/core/core.md`, or `manifest.json`.
  Nothing under `skills/`, `codex/`, `agents/`, or `.claude-plugin/` may be hand-edited.
- `npm run check` must print `generated files are up to date`. It is the gate that proves the
  build was actually run.
- `npm test` must pass. 31 tests before this change, 16 of them in `test/spec.test.mjs`; every
  new behavior adds at least one.
- `node scripts/spec.mjs validate intent-layer-gc` must report `ok` for the change after the
  delta specs are written, and again at the final gate.
- `git status --short` must show nothing added or modified under `specs/` at the repository
  root, and nothing under `hooks/`.
